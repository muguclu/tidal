## Executive summary (for the trading manager)

* **Storing the data as epoch Parquet is 3.6x smaller than the relational baseline** on the benchmark slice (MEASURED bytes). In money, 25x cheaper at rest, but the absolute amount is cents: at the full 50 M-tick scale it is EUR 0.010 versus EUR 0.258 per month (MODELLED).
* **Moving old rows out of SQL works end to end** on the local stack: the tiering job moved 2,923,720 tick rows and 1,218,173 bar rows to Parquet and SQL space fell from 137,040 KB to 34,960 KB reserved (MEASURED, local). It took 283 s of wall-clock in two runs (the first was cut short by a Docker engine restart and the second resumed it).
* **The real saving is SQL compute, not bytes.** Right-sizing from an always-on GP 2-vCore database to an auto-pausing serverless one is modelled at EUR 215 -> EUR 90 per month at S (MODELLED, NEEDS-CLOUD). It rests on an assumed 176 active hours per month; the saving disappears at 426 active hours.
* **Blob tiering by age (C3) is worth almost nothing at these sizes**: net +0.0010 / +0.0100 / +0.1108 EUR per month at S / M / L (MODELLED). It is only positive because we tag ticks only, with two tags (ADR-0015); the earlier design was a net loss. It is a correctness-of-design point, not a budget lever.
* **Nothing here is a real Azure bill.** Every Azure EUR figure is list price times a measured or assumed quantity. Real billing and the tier-capacity metric need a deployed environment (NEEDS-CLOUD).

## C1. Epoch time-series format: F0 vs F5

Source: T-204 raw results (`storage-benchmark-2026-10-22.parquet`), bytes MEASURED; EUR = GiB x unit price (MODELLED). F0 is priced as SQL GP storage (`sql_gp_storage_gb_month` 0.1204), F5 as Blob Hot (`blob_hot_stored_gb_month` 0.0172). F0 billed basis is the SQL-reserved size (103,161,856 B).

| Scale | Ticks | F0 bytes | F5 bytes | F0 B/tick | F5 B/tick | F0 EUR/month | F5 EUR/month |
|---|---|---|---|---|---|---|---|
| S-3m (MEASURED bytes) | 2,243,908 | 103,129,088 | 28,413,681 | 45.96 | 12.66 | 0.01157 | 0.00046 |
| S full (F5 MEASURED, F0 MODELLED) | 50,083,533 | 2,301,818,560 | 632,371,312 | 45.96 | 12.63 | 0.25811 | 0.01013 |

Adjusted F0 (without the extra `ts_sub` column F0 needs for nanosecond accuracy): 100,882,625 B (3.6x F5).

**S-3m caveat.** F0 (and F1, F2) was run only on a 3-month slice of S (2.24 M ticks) because the SQL load ran at 1.4k-15k rows/s and the full run was not feasible. The full-S F0 row above is therefore the S-3m bytes/tick (45.96) multiplied by the full tick count: MODELLED. The extrapolation is supported for files (F5: 12.66 B/tick at S-3m versus 12.63 at full S, 0.3 % apart) but is untested for SQL rowstore. A B-tree with a fixed row width should be close to linear, but fill factor and page splits are not measured at full S. The full-S F5 figure is MEASURED: 632,371,312 B = 12.63 bytes/tick.

Trade-off: F5 is a file format. Point lookups are slower than a clustered index (T-204 W4 factor 0.3x), writes are append-only per instrument-month, and there is no row-level update; restatements are new versions. Analytical scans are faster (T-204). Operational effort: compaction and tagging jobs (SPEC-03).

## C2. SQL to object storage migration

### Measured: one local `tidal tiering run`

Command (inside the dev image, compose stack): `TIDAL_CLOCK__NOW=2026-10-24T00:00:00Z tidal tiering run` (hot window 90 d, defaults for batch/delete chunk). The clock is frozen so the window is repeatable. Dry run first (plan only), then the real run. Local SQL Server 2022 Developer in Docker plus Azurite; not Azure.

| Table | Rows planned (dry run) | Rows moved, run 1 | Rows moved, run 2 | SQL rows left | Parquet bytes written | `sp_spaceused` reserved KB before | after |
|---|---|---|---|---|---|---|---|
| md.tick_hot | 2,923,720 | 1,600,722 (cut short) | 1,322,998 | 0 | 36,843,887 | 71,368 | 2,184 |
| md.bar_hot | 1,218,929 in table, 1,218,173 older than the window | 1,218,173 | 0 | 756 (inside the 90 d window) | 35,708,631 | 65,672 | 32,776 |

Timings (MEASURED wall-clock of each `docker compose run`, including container start): dry run 148 s; real run 1 142 s (exit 1); real run 2 141 s (exit 0). Run 1 moved all bars and part of the ticks, then lost its SQL connection when the Docker engine restarted (`08S01 communication link failure`, an environment event, not a job defect). The job is resumable by design (rows are deleted from SQL only after the Parquet is verified; the watermark advances only when a table finishes), and run 2 moved exactly the remaining rows with 0 errors and 0 deduped. Total Parquet bytes per dataset are read back from Azurite (`c2/blobs_created.json`, helper `c2/list_blobs.py`); the bar bytes equal the run-1 log. After the runs `md.tick_hot` is empty (`c2/sql_state_after.txt`; a fresh `sp_spaceused` shows 200 KB reserved, the 2,184 KB in the run-2 log was taken before ghost cleanup, because `space_used_kb` does not use `@updateusage`). The machine was shared with other containers.

Measured ratio on ticks: SQL 25.00 B/tick reserved (rowstore, tick_hot with its index), Parquet 12.60 B/tick written (36,843,887 B over 2,923,720 ticks), so object storage holds 50 % of the SQL bytes (2.0x smaller). Bars are not used in the cost model below (ticks dominate bytes).

### Modelled: Azure EUR (NEEDS-CLOUD for real billing)

Assumptions (stated, not measured): history of S = 50,000,000 ticks over 5 y, M = 300,000,000 ticks over 10 y, L = 1,500,000,000 ticks over 20 y (T-121 10 B/row sizes; config-contract scales). Baseline: GP provisioned 2 vCore always on (2 x 730 h x 0.1473 EUR) plus all ticks in SQL storage at 0.1204 EUR/GiB-month. Optimised: last 90 d in serverless SQL (1 vCore average x 176 active h x 0.505 EUR, auto-paused otherwise), older rows as Parquet on Blob Hot (0.0172 EUR/GiB-month), 100,000 cold-path queries/month at 0.0093 EUR per 1,000 (T-204 W3 request counts 5 GET + 7 HEAD + 1 LIST, `blob_hot_read_10k` for GET and HEAD, `blob_hot_write_10k` for LIST, as in the T-204 report). Bytes use the measured SQL and Parquet bytes/tick above. The `sql_gp_provisioned_vcore_hour` meter may exclude licence cost (see its note in prices.yaml), so the baseline is a lower bound.

Storage bytes shrink by the measured ratio but are cents at every scale; the difference is dominated by compute. Break-even serverless active hours at S (compute only, 1 vCore average): 426 h/month of 730. The serverless saving therefore depends on the auto-pause duty cycle, which is a usage assumption, not a property of the migration. Hidden costs counted: cold-path read transactions. Not counted: egress (same region, none), early deletion (Hot tier has none), log ingestion (C-series elsewhere), Service Bus and Container Apps compute for the tiering job.

Trade-offs: queries older than 90 d go through DuckDB over Blob (higher first-byte latency, per-query transaction cost), serverless adds a cold-start (resume) delay of the first query after a pause, and the tiering job is another moving part (watermark, applock, verify-before-delete; crash-safe and idempotent per SPEC-03). Restatements of tiered months re-version rows (ADR-0014).

## What would change the conclusions

* C1: a measured F0 at full S (bytes/tick drifting with fill factor) would move the extrapolated F0 row; real tick data compresses differently from the synthetic generator.
* C2: the serverless active hours (176/month assumed), the vCore average, and whether the provisioned meter includes a licence. A real invoice replaces the whole table. Break-even is 426 h/month at 1 vCore.
* C3: part size and part count (tags are billed per tagged blob), the real tick volume per instrument, and whether Cool/Cold prices stay as captured. Larger L-scale data and many small parts flip the sign.
