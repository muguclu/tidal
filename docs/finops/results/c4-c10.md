# C4 to C10: measurement method, model and local load reference (T-504)

Labels (CLAUDE.md 2.2): **MEASURED** = produced by a run, **MODELLED** = computed by
`python -I docs/finops/results/c4_c10_model.py` from `docs/finops/prices.yaml` (2026-10-24, westeurope, EUR) and the stated
scenarios, **NEEDS-CLOUD** = cannot be measured until the dev environment exists (no Azure resource was created for T-504).
Every EUR below is the script's output; re-run it to reproduce. Scenarios (node-hours, active hours, uncapped log rate, image size)
are assumptions and are replaced by measurements in the cloud window. A month is 730 h.

## Local load test (MEASURED, local only, not Azure)

`tests/load/locustfile.py`, 1 user, 120 s, constant pacing 1.3 s, read mix (bars 5, latest 5, ticks 2, spreads 2) against the
Docker Compose stack (api and query containers, Azurite as cold store, SQL Server container as hot store, auth disabled), one
laptop, local network. Raw CSVs: `docs/finops/results/load/local-run_*.csv`. Command:
`TIDAL_LOAD_BACKTEST_WEIGHT=0 uv run --group load locust -f tests/load/locustfile.py --headless -u 1 -r 1 -t 120s --host http://127.0.0.1:8000 --csv docs/finops/results/load/local-run`.

| Endpoint | Requests | Failures | p50 ms | p95 ms | p99 ms |
|---|---:|---:|---:|---:|---:|
| GET /v1/bars (1d, 2025-01 to 2026-10, mixed tier) | 29 | 0 | 97 | 1600 | 2800 |
| GET /v1/latest (2 instruments, hot) | 29 | 0 | 49 | 830 | 1200 |
| GET /v1/spreads (Brent minus WTI, mixed tier) | 17 | 0 | 130 | 2100 | 2100 |
| GET /v1/ticks (2 days, 200 rows, hot) | 14 | 0 | 130 | 590 | 590 |
| **Aggregated** | **89** | **0 (0.00 %)** | **91** | **1100** | **2800** |

Caveats, read before using these numbers:

- Small sample (89 requests): the p95/p99 of each endpoint are one or two requests. The first requests after a container restart
  include DuckDB Azure extension and connection warm-up, which is where the multi-second tail comes from. Use the p50 as the
  stable figure; treat the tail as an upper bound of a local stack, not as a cold start.
- Local single machine, Docker Desktop: not Azure, no network latency, no Entra auth. It is the **C5 baseline latency
  reference** (warm replica, same code) and nothing more.
- The API enforces 60 requests/minute per principal (SPEC-04 section 3). A first probe with 5 anonymous users (one shared
  principal) returned 65 % HTTP 429 (289 of 443 requests, `local-ratelimit-probe-5users_*.csv`): that run measures the limiter, not
  endpoint latency, which is why the reported run uses one user at about 46 requests/minute. Cloud load needs one token per simulated principal.
- `POST /v1/backtests` is in the locustfile but excluded from the local run (`TIDAL_LOAD_BACKTEST_WEIGHT=0`): the compose api
  answers `503 The message bus is not configured` (no Service Bus wiring for submit in the local stack). Its latency and
  accepted-rate are NEEDS-CLOUD (or a local stack with the bus wired).
- Not run: the `cold` profile (2005-onwards ranges) and any concurrency above one principal.

## C4 Dynamic autoscaling (AKS spot, KEDA 0..N) - NEEDS-CLOUD

| | Baseline | Optimised |
|---|---|---|
| Config | 5 x D4as_v5 on demand 24/7 | KEDA ScaledJob 0..N on a D4as_v5 spot pool, min 0 |
| Metric | EUR/100 backtests, idle EUR | same |
| MODELLED | 667.95 EUR/month (compute) | light (40 node-h) 1.63, heavy (150 node-h) 6.12 EUR/month incl. 32 GB OS disk; idle 0.00 |
| Saving | | 666.32 / 661.83 EUR/month (99.8 % / 99.1 %) |

The 40/150 node-hour scenarios are assumptions (T-306 delta); spot/on-demand price ratio 0.185. EUR/100 backtests needs
node-hours per 100 backtests, which only a sweep on AKS gives.

Method when the env exists: submit a sweep of known size (for example 100 children via `POST /v1/backtests` with `sweep`). Node-hours by pool:
Cost Management filtered to the `MC_*` resource group, grouped by resource, spot pool VMSS only (the T-502 export is resource-group scoped and does NOT
include the `MC_*` group, so use a subscription-scope export or the portal cost analysis, read-only). EUR/100 backtests = spot-pool cost for the
sweep window / (children / 100). Idle EUR = cost over a 24 h window with no sweep (expect OS disk only). Also record evictions (redelivered
Service Bus messages) and time to first node. Status: **NEEDS-CLOUD**.

## C5 Serverless containers (Container Apps min 0 vs always-on App Service B2) - NEEDS-CLOUD

| | Baseline | Optimised |
|---|---|---|
| Config | query service on always-on B2 | Container Apps, min replicas 0 |
| Metric | EUR/month, p95 cold-start latency | same |
| MODELLED | 23.14 EUR/month (730 h x 0.0317) | 0.00 priced: typical month is 50 % of the free grants (90,000 of 180,000 vCPU-s, 180,000 of 360,000 GiB-s) |
| Saving | | 23.14 EUR/month; compute meters round to 0.0 in the retail API, so the true figure is MEASURED from the cost export |

**Trade-off (SPEC-09 section 4): scale-to-zero pays in latency.** The first request after idle waits for replica start, image pull
and DuckDB Azure extension load. Local reference (warm, MEASURED): aggregated p50 91 ms, bars p50 97 ms; the p95 is dominated by
warm-up and is not a Container Apps cold start. The cloud cold-start p95 is NEEDS-CLOUD and is the price of the saving; the
mitigation lever is `min_replicas = 1` (cost: the replica's idle-rate vCPU/GiB seconds, measured from the export).

Method when the env exists: (1) scale to zero (poll the `Replicas` metric until 0, no sleeps); (2) send one `GET /v1/bars` and record
time-to-first-byte, repeat 20 times with idle gaps longer than the scale-down window, report p95; (3) warm comparison: run the same
locustfile against the FQDN with one token per user; (4) replica seconds: metric `Replicas` and `UsageNanoCores` for `tidal-query`, and the Microsoft.App
lines of the T-502 export (`make cost-report`). KQL for starts per hour:
`ContainerAppSystemLogs_CL | where Reason_s == "ContainerStarted" | summarize count() by bin(TimeGenerated, 1h)`. Status: **NEEDS-CLOUD**.

## C6 SQL serverless auto-pause vs provisioned GP 2 vCore - NEEDS-CLOUD

| | Baseline | Optimised |
|---|---|---|
| Config | provisioned GP 2 vCore | serverless 0.5..2 vCore, auto-pause 60 min |
| Metric | EUR/month, resume latency | same |
| MODELLED | 218.91 EUR/month (lower bound: the API shows no separate licence meter) | 40 active h: 13.95 (0.5 vCore) to 44.25 (2 vCore); paused all month 3.85 (storage) |
| Saving | | 204.96 / 174.66 / 215.06 EUR/month |

Trade-off: the first connection after a pause fails or waits tens of seconds while the database resumes, and up to 60 min of
idle after the last connection is billed at the active rate (at least 0.5 vCore). The dev environment uses the free offer
(ADR-0011), whose cost is about 0 but which pauses until next month after its allowance is used; the rows above are list price.

Method when the env exists: metric `app_cpu_billed` (vCore-seconds) on the database in Azure Monitor, summed over a month; resume latency:
let it pause (poll until `app_cpu_billed` is 0 for the interval), then time the first `SELECT 1` through `sqlcmd` and through an API call that
needs SQL (`GET /v1/latest`), repeat 10 times, report median and max. Cost from Cost Management by the serverless "vCore" meter. Status: **NEEDS-CLOUD**.

## C8 Log ingestion control - NEEDS-CLOUD

| | Baseline | Optimised |
|---|---|---|
| Config | default diagnostic settings, no cap | 0.2 GB/day daily cap, SDK sampling 20 %, optional Basic Logs table |
| Metric | GB ingested/day | same |
| MODELLED | uncapped, assumed 0.5 / 1 GB/day: 26.31 / 65.78 EUR/month (first 5 GB free, then 2.6311/GB) | ceiling 6 GB/month: 2.63 EUR/month |
| Saving | | 23.68 / 63.15 EUR/month |

The baseline rates are assumptions; the real uncapped rate is what the first measurement gives. Moving the capped 6 GB to a Basic Logs table
(0.572 EUR/GB, no free tier) would cost 3.43 EUR, more than the Analytics path, so Basic Logs only pays for a high-volume table above the free 5 GB.
Trade-off: when the cap is hit, ingestion stops for the day (diagnostics after that point are lost).

Method when the env exists: KQL on the workspace
`Usage | where TimeGenerated > ago(30d) and IsBillable == true | summarize GB = sum(Quantity) / 1000 by bin(TimeGenerated, 1d), DataType`
and `_LogOperation | where Operation == "Ingestion" and Detail has "OverQuota"` for cap hits. Sampling check: `AppRequests | summarize count()` against the request count in
the API metrics (expect about 20 %). For the baseline, run the environment once with the cap removed for 24 h. Status: **NEEDS-CLOUD**.

## C9 ACR hygiene - NEEDS-CLOUD

| | Baseline | Optimised |
|---|---|---|
| Config | no purge | weekly `acr purge` of untagged and small images |
| Metric | GB stored | same |
| MODELLED (assumed 40 images/month x 0.25 GB, 10 GB included, 0.088 EUR/GB-month above) | month 3: 30 GB, 1.76 EUR; month 6: 60 GB, 4.40 EUR; month 12: 120 GB, 9.68 EUR | 0.00 (stays within the included 10 GB) |

Image size and merge cadence are assumptions (the local dev image is 1.22 GB uncompressed; registry size is compressed, shared layers). The
saving is small in absolute EUR; the point is the unbounded growth of the no-purge baseline.

Method when the env exists: metric `StorageUsed` on the registry (Azure Monitor) or `az acr show-usage -n <registry>`; push N CI-style images, record GB, run
`az acr task run -n weekly-purge` (T-122 delta procedure), record GB after; EUR = max(0, GB - 10) x 0.088. Status: **NEEDS-CLOUD**.

## C10 Parking (`make park`) - NEEDS-CLOUD

| | Baseline | Optimised |
|---|---|---|
| Config | env always on | `make park` outside work hours (50 h/week) |
| Metric | EUR/month, cost by day | same |
| MODELLED (AKS system pool, App Service, retained disk/LB/IP) | 66.72 EUR/month | 36.95 outside work hours; 24.38 for a fully parked month |
| Saving | | 29.77 (work hours only), 42.34 (whole month) |

Trade-off: the AKS load balancer, public IP and OS disk are assumed retained while stopped (UNVERIFIED, T-306 finding; if Azure releases them the parked
figure drops to the 5.11 disk). ACR, storage and SQL are not parked and are identical in both cases.
`terraform destroy` at the end of the window remains the real cost control.

Method when the env exists: run `make park` and `make unpark` (`PARK_ARGS=--dry-run` first), then read daily cost from the T-502 export (`make cost-report`, daily
section): a parked day should show only the retained lines. Compare a parked day with an active day of the same week. Granularity is per day (the export is daily),
so work-hour parking within a day is not visible and the 36.95 figure stays MODELLED. The AKS `MC_*` group is outside the resource-group scoped export (T-502 trade-off). Status: **NEEDS-CLOUD**.
